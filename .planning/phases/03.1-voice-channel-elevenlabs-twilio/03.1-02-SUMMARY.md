## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Outer-tx-for-gate / inner-tx-for-Phase-2 split for create-order + discount**
- **Found during:** Task 1 — designing create-order voice handler
- **Issue:** The plan template wraps `createOrderHandler` inside `app.db.transaction(...)` so the advisory lock + idempotency INSERT share one tx. But Phase 2 `createOrderHandler` opens its OWN `ctx.db.transaction(...)` internally (see `apps/api/src/pipeline/llm-tools/create-order.ts:50`). Nesting them would attempt to acquire the same `pg_advisory_xact_lock` on the inner tx → potential deadlock (or, depending on Postgres semantics, the inner SELECT FOR UPDATE blocking the outer). Phase 2 was written for the Anthropic intake path which never holds a per-conversation advisory lock on the outer tx.
- **Fix:** Split into two transactions: outer tx records `webhook_updates` ON CONFLICT DO NOTHING + acquires `pg_advisory_xact_lock(hashtext(conv))` + reads Redis voice state → returns gate object → COMMIT (lock released). Then call Phase 2 `createOrderHandler(ctx, {lead_id, confirmed:true})` which runs its own tx with SELECT FOR UPDATE on the lead row (row-level lock prevents concurrent create-orders). Same split for discount.
- **Files modified:** `apps/api/src/channels/voice/tool-handlers.ts`
- **Verification:** voice-fsm-concurrency.test.ts asserts 100x concurrent create-order → exactly 1 ok=true and exactly 1 orders row. The CAS UPDATE on `leads.version` inside Phase 2 createOrderHandler is sufficient — advisory lock is a defense-in-depth layer, not the sole guard.
- **Committed in:** `5d16220` (Task 1)

**2. [Rule 1 - Bug] CallbackBaseSchema.metadata uses .loose() not .passthrough()**
- **Found during:** Task 1 — typecheck failure on `.passthrough()`
- **Issue:** Zod v4 (the project's pinned version) renamed `.passthrough()` to `.loose()`. Plan template used `.passthrough()`.
- **Fix:** Changed to `.loose()`.
- **Files modified:** `apps/api/src/channels/voice/tool-handlers.ts`
- **Verification:** `pnpm --filter @ai-logist/api typecheck` exit 0.
- **Committed in:** `5d16220` (Task 1)

**3. [Rule 2 - Missing critical functionality] Sticky lang via NOT EXISTS subquery (clients.lang is NOT NULL)**
- **Found during:** Task 2 — reading apps/api/src/persistence/schema/clients.ts
- **Issue:** Plan template says lang-detected handler sets clients.lang ONLY when NULL. But `apps/api/drizzle/0001_init.sql:43` declares `clients.lang client_lang DEFAULT 'ru' NOT NULL` — there is no NULL state to gate on. Phase 2 intake.ts (line 178) has the same problem and its `if (!client.lang)` branch is therefore dead code in the production schema. Phase 2 was permitted to ship that way because no test asserted sticky semantics directly; Phase 3.1 voice-lang-detect.test.ts DOES (the second call from the same phone must NOT flip clients.lang). Without a workaround the test would fail.
- **Fix:** Sticky guard becomes "set clients.lang ONLY if no sibling call for this client already has a non-null calls.lang." The first lang-detected event for any of a client's calls persists; subsequent events on later calls do NOT change clients.lang (but DO set their own calls.lang). Implemented via `UPDATE clients SET lang = ... WHERE id = (SELECT client_id FROM calls JOIN leads ...) AND NOT EXISTS (SELECT 1 FROM calls sibling JOIN leads sl ON sl.id = sibling.lead_id WHERE sl.client_id = clients.id AND sibling.lang IS NOT NULL AND sibling.elevenlabs_conversation_id <> $1)`. Preserves CONTEXT D-16/D-17 sticky semantics without a schema migration. Documented in call-lifecycle.ts header comment.
- **Files modified:** `apps/api/src/channels/voice/call-lifecycle.ts`
- **Verification:** voice-lang-detect.test.ts asserts: call 1 lang-detected 'ua' → clients.lang='ua'; call 2 from same phone lang-detected 'ru' → clients.lang stays 'ua' but calls.lang for call 2 = 'ru'.
- **Committed in:** `b813aa2` (Task 2)
