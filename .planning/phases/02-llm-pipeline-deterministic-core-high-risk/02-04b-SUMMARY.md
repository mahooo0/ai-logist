## Closure of Pitfall #1 (LLM in Money Path) — Final Code-Level Proof

Three layers of defense, all visible in the same canonical scenario:

1. **Tool boundary (Plan 02-02):** `createOrderHandler` input schema rejects any `price` field via `.strict()`.
2. **DB re-read (Plan 02-02):** `createOrderHandler` SELECTs `quoted_price` FOR UPDATE before INSERTing `orders.price`.
3. **Price-lock at intake (Plan 02-04b Step I):** `leads.quoted_price` is WRITTEN before any reply text is built. The audit-log row `lead_events.QUOTED.payload.quoted_price` carries the same value; `pipeline-canonical.test.ts` asserts the row's `created_at` is ≤ the last assistant message's `created_at`, proving the write happened before the reply.

The canonical test verifies the end-to-end invariant: `orders.price === leads.quoted_price` after both message turns. This is the ROADMAP success criterion #1 closure.

## Closure of FSM-06 — Scheduler Lifecycle Proof

The fake-timer test exercises the full setInterval lifecycle deterministically:

```
vi.useFakeTimers({ shouldAdvanceTime: true, now: FROZEN_NOW })
  ↓
INSERT lead at FROZEN_NOW
  ↓
registerFollowUpScheduler(app) [sets up setInterval + onClose hook]
  ↓
vi.setSystemTime(FROZEN_NOW + 25h)
  ↓
vi.advanceTimersByTimeAsync(POLL_INTERVAL_MS) [fires tick]
  ↓
followUpTick reads NOW() in JS land → finds the lead stale → transitionLead → LOST
  ↓
assert lead.stage === 'LOST' + payload.reason === 'no_reply_24h'
  ↓
await app.close() [onClose hook fires clearInterval]
  ↓
INSERT lead 2 at FROZEN_NOW
  ↓
vi.setSystemTime(FROZEN_NOW + 50h) + advance
  ↓
assert lead 2 STILL QUOTED (no further ticks)
```

The `shouldAdvanceTime: true` knob is critical — without it, `await db.execute(...)` inside the tick callback never resolves because the underlying promise microtask scheduler sees frozen time. Combining `shouldAdvanceTime` with `setSystemTime` lets us fast-forward the wall clock that `followUpTick` reads for its `staleCutoff` calculation while keeping the JS event loop alive.
